# dokploy-mcp v2.2.0 - Response shaping and workflow ergonomics plan

**Goal:** reduce token waste and discovery calls in Code Mode without breaking the current `search` + `execute` contract.

**Status:** repo-local implementation completed on March 25, 2026; upstream alignment still pending

**Current package version:** `2.1.1`

**Primary feedback being addressed:**

1. Add `select` support for heavy detail endpoints such as `application.one`
2. Exclude or limit deployments by default only when explicitly requested
3. Add a batch read path for multiple applications
4. Add a project-level overview path for the most common inspection workflow
5. Teach the model what important endpoints return without forcing a discovery call

**Current verified constraints on March 25, 2026 after the latest implementation slices:**

- The public MCP surface remains exactly two tools: `search` and `execute`
- Tool descriptions are currently small: about `2381` bytes total, around `595` tokens
- `application.one` and `project.one` currently expose empty generated response schemas
- `execute` response budgeting counts bytes after the gateway returns data to the sandbox host
- Generated artifacts under `src/generated/*` are rebuilt from OpenAPI and must not be edited manually

---

## Why this plan

The feedback is valid. Today the model often has to either:

- call a heavy detail endpoint and overpay in tokens, or
- call `search` and still not learn the real response shape, because the generated OpenAPI output schema is empty for some important procedures

The lowest-risk path is to improve this in layers:

1. enrich discovery first
2. add response shaping for the heaviest endpoint
3. only then add fan-out virtual procedures, because those require accurate call accounting

This sequence gives immediate value while keeping backward compatibility and preserving the current Code Mode design.

---

## Product decisions

### Public contract decisions

- Keep only `search` and `execute` as public MCP tools
- Do not change default behavior of existing procedures
- Add MCP-only input parameters only as optional fields
- Prefer upstream Dokploy API improvements for true server-side savings
- Allow MCP-side shaping when it reduces model tokens and `execute` byte budget, even if it does not reduce upstream network payloads

### Architecture decisions

- Do not hand-edit `src/generated/*`
- Add a non-generated overlay layer that can:
  - extend input schemas for selected procedures
  - add manual response hints for discovery
  - register MCP-only virtual procedures such as `application.many` and `project.overview`
- Apply response shaping inside the gateway, before the sandbox host counts response bytes
- Count fan-out virtual procedures against the real underlying Dokploy call budget

### Scope decisions

- `application.one` is the first shaping target
- `application.many` and `project.overview` are phase-2 features, not phase-1
- `deploymentLimit` stays relevant even after `select`, because some workflows still want deployment data but only the latest item
- `includeDeployments: false` is acceptable sugar, but `deploymentLimit` is the more general primitive

---

## Target outcomes

By the end of v2.2.0:

- `catalog.get('application.one')` and similar key procedures provide useful response-shape hints
- `execute` can run `await dokploy.application.one({ applicationId, select: [...] })`
- `execute` can trim or omit deployments before response bytes are counted
- the model can discover at least the most common response shapes without making an exploratory API call
- if `application.many` and `project.overview` ship, they do not bypass sandbox call limits

## Phase 2 - `application.one` response shaping (ship in v2.2.0)

**Purpose:** cut the biggest avoidable token sink while keeping backward compatibility.

### Input contract

Add optional MCP-only fields to `application.one`:

- `select?: string[]`
- `includeDeployments?: boolean`
- `deploymentLimit?: number`

### Contract rules

- Without these fields, behavior is unchanged
- `select` returns only the requested top-level fields
- `includeDeployments: false` removes the `deployments` field from the returned object
- `deploymentLimit` truncates the `deployments` array when it is present
- reject invalid combinations such as `includeDeployments: false` together with `deploymentLimit`

### Design choice for `select`

v2.2.0 should support top-level fields only.

Reasoning:

- it matches the feedback examples
- it is much simpler to document and validate
- it avoids ambiguity around nested path syntax
- it can be extended later to dotted paths if real usage justifies it

### Required implementation work

- Extend the effective input schema for `application.one`
- Add a projection utility, for example:
  - `pickSelectedFields(value, select)`
  - `applyDeploymentControls(value, includeDeployments, deploymentLimit)`
- Run shaping in the gateway after the upstream response is received and before the sandbox host counts bytes
- Make the search catalog advertise the new optional fields for `application.one`
- Add or update execute integration tests covering:
  - full response, unchanged default behavior
  - `select`
  - `includeDeployments: false`
  - `deploymentLimit: 1`
  - invalid combinations

### Expected output behavior

Example:

```js
await dokploy.application.one({
  applicationId: 'app-123',
  select: ['name', 'applicationStatus', 'mounts', 'watchPaths'],
})
```

returns only the selected fields that exist on the upstream object.

### Acceptance criteria

- `application.one` stays backward compatible
- shaped responses reduce `execute` response bytes for heavy application payloads
- validation errors are clear when optional shaping parameters are invalid
- search discovery shows the new optional fields

## Phase 3 - Virtual batch read: `application.many` (gated by Phase 0)

**Purpose:** reduce repeated workflow code and improve ergonomics when inspecting several apps.

### Product position

This is valuable, but it is an MCP-side aggregation unless Dokploy adds a real upstream batch endpoint.

That means it improves:

- model workflow simplicity
- final response token size
- local orchestration convenience

It does not automatically improve:

- upstream network round-trips
- upstream server work

### Proposed input contract

- `applicationIds: string[]`
- `select?: string[]`
- `includeDeployments?: boolean`
- `deploymentLimit?: number`

### Proposed output contract

Return an object rather than a bare array:

- `items: Array<Record<string, unknown>>`
- `total: number`
- `missingIds?: string[]`

This gives the model a stable place for partial failures without inventing exceptions for every missing application.

### Required implementation work

- Register `application.many` as a virtual procedure in the override layer
- Implement the handler by calling `application.one` per ID through the same gateway shaping path
- Charge the real number of underlying Dokploy calls against the execute budget
- Preserve input order in the output
- Define whether missing apps are collected in `missingIds` or fail the whole call

### Recommended behavior

- default: fail the whole call on the first Dokploy error
- optional future extension: `skipMissing?: boolean`

### Acceptance criteria

- `application.many` is discoverable through `search`
- a call for 10 app IDs is charged as 10 upstream calls
- `select` and deployment controls behave the same as in `application.one`
- output order matches input order

## Phase 4 - Project aggregate read: `project.overview` (best handled upstream, optional MCP stopgap)

**Purpose:** support the common request: "show me the state of all services in this project".

### Product position

This is the highest-value aggregate read in the feedback.

If Dokploy can expose it upstream, that is the preferred long-term design.

If Dokploy cannot expose it yet, MCP can ship a stopgap virtual procedure after Phase 0 accounting is in place.

### Proposed output shape

An opinionated overview is better than a generic dump.

Recommended per-application fields:

- `applicationId`
- `name`
- `appName`
- `applicationStatus`
- `domains`
- `mounts`
- `watchPaths`
- `lastDeployment`

Recommended project-level shape:

- `projectId`
- `name`
- `environments`

Where each environment contains:

- `environmentId`
- `name`
- `applications`

### Implementation options

**Preferred:** upstream Dokploy endpoint

- one real API call
- real server-side selectivity
- real network and compute savings
- cleaner OpenAPI generation

**Fallback:** MCP virtual procedure

- call `project.one`
- collect application references
- call `application.one` for each app with a narrow `select`
- shape `lastDeployment` from `deployments[0]` after applying `deploymentLimit: 1`

### Gating rule

Do not ship MCP-side `project.overview` until the real underlying call accounting is complete.

### Acceptance criteria

- overview output is opinionated and compact
- deployments are limited to the latest item only
- call budgeting remains honest
- docs clearly mark this as MCP-only unless and until Dokploy ships it upstream

## Risks and mitigations

### Risk: manual hints drift from real payloads

Mitigation:

- keep hints limited to common fields, not full contracts
- prefer upstream schema fixes whenever possible
- verify key endpoints against live read-only responses before release

### Risk: virtual procedures hide true cost

Mitigation:

- Phase 0 accounting is mandatory before shipping fan-out helpers
- add tests that assert budget consumption equals underlying call count

### Risk: tool descriptions bloat the tools/list payload

Mitigation:

- keep top-level tool descriptions short
- put richer guidance in `catalog.get()` instead of the global tool description
- check the budget script before release

### Risk: `select` semantics become confusing

Mitigation:

- support top-level fields only in v2.2.0
- reject invalid combinations clearly
- document the exact behavior with examples

### Risk: MCP-only parameters diverge from upstream Dokploy naming

Mitigation:

- use clear docs and search hints
- prefer parameter names that Dokploy could also adopt upstream later
