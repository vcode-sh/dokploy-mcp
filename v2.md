# dokploy-mcp v2.0.0

## Code Mode architecture, performance audit, and implementation plan

## 1. Objective

Redesign `@vibetools/dokploy-mcp` around a Cloudflare-style Code Mode architecture so that:

- the MCP protocol surface is tiny and stable
- the agent can still access the full Dokploy API
- multi-step workflows execute mostly outside the model loop
- token cost becomes effectively independent of endpoint count
- the server becomes easier to scale to `100%` API coverage than the current one-tool-per-endpoint model

This document is the implementation plan for v2.0.0, not a brainstorm note.

It is intended to be actionable by an implementation agent or engineering team without needing further architecture clarification.

## 2. Source material

Primary references:

- Cloudflare, **"Code Mode: the better way to use MCP"** (2025-09-26)
  - https://blog.cloudflare.com/code-mode/
- Cloudflare, **"Code Mode: give agents an entire API in 1,000 tokens"** (2026-02-20)
  - https://blog.cloudflare.com/code-mode-mcp/

Key takeaways extracted from those sources:

1. Presenting an API as hundreds or thousands of individual MCP tools does not scale for model context.
2. A fixed MCP surface with `search()` and `execute()` can compress a very large API into a small token footprint.
3. Letting the model write code for orchestration is far more efficient than round-tripping every intermediate step through tool calls.
4. The execution environment must be a secure sandbox with no direct access to filesystem, env vars, or unrestricted outbound network.
5. The server should own capability discovery and execution; the client should remain simple.

## 3.2 Protocol cost

Measured from the current built server:

- `tools/list` payload size: approximately `369,416` bytes
- rough prompt cost: approximately `92,354` tokens at `~4 chars/token`

This is the main performance problem.

For comparison:

- Cloudflare's Code Mode MCP surface is intentionally fixed to roughly `1,000` tokens
- our current server is about two orders of magnitude larger at discovery time

## 3.3 Tool payload concentration

Top per-module contributors to `tools/list` payload:

| Module | Tools | Approx bytes in `tools/list` |
|---|---:|---:|
| `application` | 29 | `54,293` |
| `notification` | 38 | `49,786` |
| `compose` | 28 | `28,627` |
| `settings` | 49 | `24,953` |
| `mariadb` | 14 | `14,227` |
| `postgres` | 14 | `14,111` |
| `mysql` | 14 | `14,095` |
| `mongo` | 14 | `14,051` |
| `redis` | 14 | `13,681` |
| `server` | 16 | `11,532` |

Implications:

- the biggest payload drivers are not only the biggest modules
- large schemas and high-property tools dominate cost more than titles
- databases as a group are expensive even though each module is structurally repetitive

## 3.4 Human text overhead

Measured text-only overhead:

- `name` + `title` + `description` + schema keys: approximately `93,599` bytes

If descriptions and annotations were heavily trimmed, the total `tools/list` payload would still remain far too large. The problem is structural, not editorial.

## 3.5 Architectural limitations

### A. Token footprint scales linearly with API coverage

Every newly implemented endpoint increases:

- MCP registration count
- schema payload
- prompt footprint
- tool ranking/search burden for the model

This is the exact opposite of the desired scaling model.

### B. Multi-step workflows are inefficient

Today the only composition model is:

1. model chooses tool
2. tool executes
3. result goes back into model context
4. model chooses next tool
5. repeat

This means:

- every intermediate payload consumes tokens
- every step adds latency
- the model must repeatedly re-orient on the same task

### C. Discovery burden is high

At `377` tools:

- tool ranking quality becomes model-dependent
- semantically similar tools compete for attention
- clients with weak MCP UX suffer more

### D. Maintenance cost is high

The current model requires hand-maintained files for each module and often each endpoint class. This is acceptable for v1 but not a scalable strategy for v2 if the goal is full API parity.

## 3.6 Functional strengths to preserve

v2.0.0 should preserve:

- OpenAPI-driven correctness mindset
- accurate schemas
- tRPC request/response normalization
- compact, useful error mapping
- broad endpoint coverage
- tests and coverage guard discipline

v2 is an architectural pivot, not a rewrite-for-rewrite's-sake.

## 4. Why Cloudflare's approach matters here

Cloudflare solved a problem that is almost identical to ours:

- huge API surface
- too many MCP tools
- context window pressure
- poor scalability of direct tool exposure

The most important thing they optimized was not raw HTTP latency. They optimized:

1. **discovery cost**
2. **orchestration cost**
3. **prompt footprint**
4. **sandbox safety**

Their system-level decisions we should copy:

### 4.1 Fixed MCP surface

Instead of exposing the whole API:

- expose `search`
- expose `execute`

This keeps `tools/list` stable and small.

### 4.2 Pre-processed API representation

Instead of loading the full OpenAPI into the model prompt:

- build a resolved, indexed representation server-side
- let the model query it through code

### 4.3 Server-side code execution

Instead of asking the model to tool-call each step:

- let the model write code that performs many API requests in one run

### 4.4 Strong sandbox boundary

Cloudflare's advantages depend heavily on:

- isolate sandboxing
- no direct secret access
- no direct internet by default

This must be treated as a hard requirement, not a nice-to-have.

## 5. v2.0.0 product decision

This plan assumes one end-to-end implementation wave for `v2.0.0`.

The sections below are execution order, not separate release slices.

## 5.1 Default mode

`v2.0.0` should ship Code Mode as the default MCP server behavior.

## 5.2 Compatibility mode

Keep the current classic architecture only as a migration bridge.

Recommended package behavior:

- `dokploy-mcp`
  - Code Mode default
- `dokploy-mcp-classic`
  - legacy one-tool-per-endpoint server

Alternative:

- one binary with `--mode codemode|classic`

Preferred approach:

- separate binaries or package entrypoints

Reason:

- avoids mixing two radically different protocol surfaces
- keeps client behavior explicit
- avoids accidentally reintroducing the large classic tool surface in the default configuration

## 5.3 Non-goals

v2.0.0 should not:

- continue scaling the classic one-tool-per-endpoint server as the primary architecture
- expose both classic and Code Mode surfaces simultaneously in one MCP server
- use shell access as the main orchestration mechanism
- give model-authored code access to Dokploy secrets or unrestricted Node capabilities

## 6. Target architecture

## 6.1 High-level shape

The v2 server should be structured into five layers:

1. **Build-time API generation**
2. **Runtime API gateway**
3. **Sandbox runtime**
4. **MCP Code Mode tools**
5. **Compatibility server**

## 6.2 MCP tools exposed in Code Mode

The default v2 server should expose:

1. `search`
2. `execute`

Optional:

3. `describe`

Preferred target:

- only `search`
- only `execute`

## 6.3 Tool: `search`

Purpose:

- discover relevant Dokploy API capabilities without loading the full API into model context

Input:

```json
{
  "code": "async ({ catalog }) => { /* search logic */ }"
}
```

Injected globals or parameters:

- `catalog.endpoints`
- `catalog.byTag`
- `catalog.byProcedure`
- `catalog.byPath`
- `catalog.get(id)`
- `catalog.searchText(query)`

Returned result must be bounded:

- max result count
- max payload size
- compact endpoint summaries

Output shape:

```json
{
  "matches": [
    {
      "procedure": "application.update",
      "method": "POST",
      "path": "/application.update",
      "tag": "application",
      "summary": "Update application",
      "required": ["applicationId"],
      "optional": ["name", "env", "buildArgs"]
    }
  ]
}
```

## 6.4 Tool: `execute`

Purpose:

- run a multi-step workflow against Dokploy in one sandboxed execution

Input:

```json
{
  "code": "async ({ dokploy, helpers }) => { /* workflow */ }"
}
```

Injected capabilities:

- `dokploy.call(procedure, input)`
- generated typed namespaces:
  - `dokploy.application.one()`
  - `dokploy.compose.search()`
  - etc.
- helpers:
  - `helpers.assert()`
  - `helpers.pick()`
  - `helpers.sleep()` only if needed
  - `helpers.paginateUntil()`
  - `helpers.limit()`
  - `helpers.selectOne()`

Execution result:

```json
{
  "result": { "...": "final answer" },
  "logs": ["searched project", "found environment", "updated application"],
  "calls": [
    { "procedure": "project.search", "ms": 72 },
    { "procedure": "environment.byProjectId", "ms": 64 },
    { "procedure": "application.update", "ms": 118 }
  ]
}
```

## 6.5 Optional tool: `describe`

Only add this if `search` cannot return sufficient per-endpoint detail efficiently.

Purpose:

- fetch one endpoint's complete contract in a compact representation

If not necessary, do not expose it.

## 6.6 Generated Dokploy SDK

Generate a TypeScript surface for the sandbox, based on OpenAPI:

```ts
declare const dokploy: {
  call<TInput, TOutput>(procedure: string, input: TInput): Promise<TOutput>
  application: {
    one(input: { applicationId: string }): Promise<Application>
    update(input: ApplicationUpdateInput): Promise<Application>
  }
  compose: {
    search(input: ComposeSearchInput): Promise<SearchResult<Compose>>
  }
}
```

Important:

- the SDK is for the sandbox, not for human package consumers
- it can be regenerated on every build
- it should cover all OpenAPI endpoints, not only today's `377`

This is how v2 should leap from partial manual coverage to effectively full API reach.

## 7.3 Catalog design

Each endpoint in the compact catalog should include only:

- procedure id
- method
- path
- tag
- short summary
- required input fields
- optional input fields
- compact response summary
- authentication flags if needed

Do not include:

- full prose descriptions by default
- full nested schemas by default

The full schema stays available through `catalog.get()`, but only on-demand inside `search`.

## 8. Sandbox architecture

This is the highest-risk workstream.

## 8.1 Security requirements

The sandbox must:

- have no filesystem access
- have no `process.env`
- have no `child_process`
- have no unrestricted `fetch`
- have no arbitrary module loading
- have a hard CPU / wall-clock timeout
- have a hard memory limit
- return JSON-serializable results only

## 8.2 Recommended runtime

Preferred:

- `isolated-vm`

Fallback:

- dedicated subprocess worker with strict IPC boundary

Do not use raw Node `vm` as the only protection boundary.

## 8.3 Supervisor/bridge model

The sandbox never talks directly to Dokploy.

Flow:

1. sandbox calls generated SDK method
2. supervisor validates procedure and input
3. supervisor executes the real HTTP request with the real API key
4. supervisor normalizes the response
5. sanitized result is returned to the sandbox

Benefits:

- secrets stay in the supervisor
- retries and telemetry stay centralized
- request policy stays consistent

## 8.4 API available inside sandbox

Only inject:

- generated `dokploy` client
- minimal helper utilities
- `console.log`

Do not inject:

- Node built-ins
- shell
- global network access
- random timers beyond what execution strictly needs

## 8.5 Execution limits

Proposed defaults:

- max wall time: `5s`
- max API calls per run: `25`
- max outbound Dokploy response aggregate: `2 MB`
- max logs: `8 KB`
- max returned result: `128 KB`

These should be configurable, but bounded.

## 9. Runtime gateway design

## 9.1 API gateway module

Create:

- `src/codemode/gateway/api-gateway.ts`

Responsibilities:

- endpoint lookup
- input validation
- Dokploy HTTP execution
- tRPC wrapping/unwrapping
- compact error formatting
- retries and backoff
- call tracing

## 9.2 Compact error responses

Inspired by Cloudflare's structured error handling direction:

- errors returned to the sandbox should be short, machine-readable, and deterministic
- no large HTML or accidental large text blobs

Recommended shape:

```json
{
  "ok": false,
  "type": "dokploy_error",
  "status": 400,
  "procedure": "compose.getTags",
  "message": "Invalid input: expected object, received undefined"
}
```

## 9.3 Request normalization

The gateway must fully own:

- GET `input={"json":...}` behavior
- zero-input GET normalization
- POST `{"json": body}` wrapping
- tRPC result unwrapping

This logic should not be duplicated across modes.

## 10.3 Execute overhead targets

Before first Dokploy API call:

- p50 `<40ms`

Representative multi-step workflow:

- `project search -> environment lookup -> application update`

Target:

- one `execute` run
- no intermediate results re-enter the model

## 14. Detailed protocol contract

## 14.1 `search` tool contract

Final `search` contract for v2 should be:

```json
{
  "code": "async ({ catalog }) => { /* return matches */ }"
}
```

Required execution model:

- the code must be an async arrow function
- the code must return JSON-serializable output
- the code must not exceed execution budget

Injected search context:

- `catalog.endpoints`
- `catalog.byTag`
- `catalog.byProcedure`
- `catalog.byPath`
- `catalog.get(id)`
- `catalog.searchText(query)`

Hard limits:

- max returned matches: `50`
- max output bytes: `32768`

## 14.2 `execute` tool contract

Final `execute` contract for v2 should be:

```json
{
  "code": "async ({ dokploy, helpers }) => { /* return final result */ }"
}
```

Injected execute context:

- `dokploy.call(procedure, input)`
- generated namespaced Dokploy SDK
- `helpers.assert`
- `helpers.pick`
- `helpers.limit`
- `helpers.paginateUntil`
- `helpers.selectOne`
- `console.log`

Hard limits:

- max API calls: `25`
- max logs: `8 KB`
- max final result: `128 KB`
- max combined Dokploy payloads: `2 MB`

Return envelope:

```json
{
  "result": {},
  "logs": [],
  "calls": []
}
```

The server, not the model, is responsible for:

- timing
- trace collection
- payload truncation
- error normalization

## 14.3 `describe` tool contract

Only implement if strictly needed.

If implemented, it must:

- accept one endpoint identifier
- return compact contract data
- not return the whole OpenAPI

## 19. Final recommendation

Do not spend v2 effort on further scaling the current one-tool-per-endpoint surface.

The numbers already show the limit:

- `377` tools
- `~92k` tokens in discovery alone

The correct v2.0.0 implementation is:

1. generated API model
2. fixed MCP surface
3. secure server-side execution
4. classic mode only for migration

That is the plan that actually follows Cloudflare's performance logic rather than just copying their vocabulary.
